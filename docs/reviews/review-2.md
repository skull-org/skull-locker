# SKULL Locker (open-source file locker) - independent review by Claude Opus (claude-opus-5-5)

> 10 Nov 2026 · code fingerprint eab33b8fef9bd02c · read-only review (no tools). Each fix is decided by the test suite.

## Verdict
**READY AFTER FIXES.** The cryptography is sound. libsodium secretstream is used correctly, the header is authenticated, the file key is random and wrapped once per secret, and the original is checked against the locked copy before it is deleted. The problems are in how the restored file is named and placed, in what the tool promises users, in the launcher, and in missing tests. Your design document's own test plan (known-answer tests, crash tests, fuzzing, a 5 GB file) has not been done yet. I reviewed this by reading the code only; I did not run it.

## Findings

| # | Severity | Where (file:function) | Problem | Fix |
|---|---|---|---|---|
| 1 | medium | locker.py:unlock | When `os.link` fails, which is normal on FAT32/exFAT USB sticks and some network shares, the code checks `dest.exists()` and then calls `os.replace(tmp, dest)`. If a file with that name appears between the check and the replace, it is silently overwritten. This breaks the promise that unlock never overwrites, on exactly the USB sticks your threat model mentions. | Claim the name atomically first with `os.open(dest, O_CREAT\|O_EXCL\|O_WRONLY)`, then `os.replace(tmp, dest)` over your own empty placeholder. On `FileExistsError`, try the next "(n)" name. |
| 2 | medium | locker.py:safe_name | The name is cut to 200 characters *after* `strip()`/`rstrip(".")`, so a crafted name can end in `.exe.` or `.exe ` after the cut. `Path("x.exe.").suffix` is `''` and `Path("x.exe ").suffix` is `'.exe '`, so no risky-file warning is shown. Windows then drops the trailing dot or space and creates `x.exe`. The reserved-name check also runs before the cut. | Cut first, keeping the extension. Then strip and `rstrip(". ")`, then run the reserved-name and risky-extension checks on the final string. Compare `suffix.rstrip(". ").lower()`. |
| 3 | medium | locker.py:lock, `__main__`.py:_gui (success text) | One overwrite with zeros does not remove the plaintext from SSD spare blocks, Volume Shadow Copies, File History, OneDrive/Dropbox version history, or editor autosaves. The GUI still says "nobody can open it". The design doc promised to tell users plainly that a secure wipe is not guaranteed; the code never does. For a lost laptop, that leftover plaintext is the main remaining risk. | Say it in the lock dialog and the CLI output: "older copies may remain in backups, cloud version history or on SSDs". Document it in the threat model. |
| 4 | medium | locker.py:lock / `_check_header` | `lock()` accepts any `ops`/`mem` with no minimum. `lock(p, pw, ops=1, mem=8192)` makes a file that passes verification and is about 8000× cheaper to brute-force. `MEM_RANGE` starts at 8 KiB, not 8 MiB. No test ever runs with the real defaults. On the other end, a received file can ask for 20 passes over 1 GiB, which freezes the GUI because the KDF runs on the UI thread. | Enforce a floor in `lock()` (for example ops ≥ 3 and mem ≥ 64 MiB) and allow lighter settings only through a private test hook. Tighten the read limits (for example mem ≤ 256 MiB, ops ≤ 10). Run the KDF off the Tk thread. |
| 5 | medium | locker.py:lock (remove step) | "Unless it changed" is checked by path using only `(st_size, st_mtime_ns)`. Writers that keep the size and restore the mtime (sync and copy tools, FAT's 2-second resolution) are not detected. The file is also opened by path three separate times (the `is_symlink` check, the read, `r+b`), so a link swapped in between can redirect the zero overwrite to another file. | Open the file once (`O_NOFOLLOW` on POSIX), read and hash through that handle, then re-hash the content through the same handle just before the wipe. Compare `st_ino`/`st_dev` as well. Do the overwrite through the same handle. |
| 6 | medium | `__main__`.py:_gui (catch-all) | The traceback is written to `~/skull_locker_error.log`. It is never removed and is overwritten on each crash. `OSError` messages raised in unlock (`os.link`/`os.replace`) contain the destination path, which is the *decrypted original name*. That is exactly the information the format encrypts, now kept in plaintext in the home folder. | Remove or redact paths before logging (log exception types and line numbers only), or ask the user before writing a log. Never log `dest`. |
| 7 | medium | `__main__`.py:menu_entries / install_menu | `-P` exists only from Python 3.11. | 8 | medium | locker.py:_copy_zone, unlock; `__main__`.py:main | The "downloaded from the internet" mark (Mark of the Web) is copied only if the `.skull` file has one. The CLI never shows `last_warning`, and `unlock.last_warning` is shared global state. | For risky extensions, write `ZoneId=3` when the source has no mark (or warn clearly). | 9 | low | `__main__`.py:main (unlock), _gui | The CLI retries as a recovery key on *any* `LockError`. | 10 | low | locker.py:_decrypt_to / _check_header | The `subkeys` flag is read from the header before the header is authenticated. When false, it switches to `(key, key)`, using one key for both secretstream and the name encryption. A forgery is still caught at the first chunk, but this is a mode switch nobody needs, since no older files exist. `norm` is never checked. | Require `subkeys is True` and `norm == "NFC"` in `_check_header`, and delete the fallback branch. |
| 11 | low | locker.py:_kdf, lock; `__main__`.py | The password, recovery key and file key are immutable `str`/`bytes` objects, held in lambdas and in the Tk widget. | 12 | low | `__main__`.py:main (lock), _gui | The CLI creates a recovery key by default without asking for confirmation. ## Missing tests
1. Truncation exactly at a chunk boundary (the whole final chunk removed). This is the case the FINAL tag exists for, and no current cut lands there.
2. In a multi-chunk file: a middle chunk swapped with another, duplicated, or removed.
3. Every single byte flipped, including the length field and the secretstream header, in a 2+ chunk file.
4. Header splicing: the header, a wrapped-key entry, or the name block from another file locked with the same password.
5. Header fuzzing (Hypothesis): ops/mem out of range, `n` > 1 MiB, bad hex, missing fields, `subkeys: false`, a repeated `by`, three keys, a non-dict, `True` as ops.
6. A known-answer test that `_subkeys` equals libsodium `crypto_kdf_derive_from_key`, plus a fixed `.skull` file in the repo that must always open (format stability).
7. One round trip with the real default OPS/MEM, and `lock()` refusing weak ops/mem (after fix #4).
8. A password typed composed vs decomposed (é, Devanagari) opens the same file.
9. Recovery-key input with spaces, dashes and upper case is accepted; 63/65 characters and non-hex are refused.
10. The original changes during lock (#4): the original is kept, the locked copy exists, and the message is correct.
11. Symlinks refused, hard links refused, and `remove_original=False` leaves the original byte-for-byte identical.
12. Crash injection: kill a subprocess at each step of lock and unlock (after the temp write, after replace, mid-overwrite, mid-unlock) and assert that the original or the locked copy is always intact.
13. Unlock with `os.link` forced to raise `OSError`: an existing name is never overwritten, including a name created during the race.
14. A table test for `safe_name`: `..`, `CON`, `con.txt`, `a:b`, RLO tricks (`fdp.exe`), trailing dots/spaces, a 200-character cut ending in `.exe.`, separators on both OSes, and the warning for each risky extension.
15. `out_dir`, a read-only destination, and no temp files left after any failure (with the corrected glob).
16. CLI and GUI unlock: wrong password, a recovery key, a truncated file showing the "cut short" message, and a 64-hex string used as a password.
17. Run the generated menu command for real (Windows CI) from a folder with a planted `json.py`/`skull_locker/`, and assert they don't run. Include a path with `'` and the Python < 3.11 refusal.
18. `_copy_zone` on a Windows runner, with and without a source mark.
19. A multi-GB file with memory use staying bounded.
20. Passwords that are empty, `None`, or 8 spaces.
21. The error log never contains the decrypted name (after fix #6).

## What is done well
- Only proven primitives through libsodium: Argon2id, XChaCha20-Poly1305 secretstream, AEAD key wrapping. No home-made crypto.
- A random file key wrapped separately by the password and the recovery key, so the recovery key needs no KDF.
- The header is the first chunk's associated data, and the length prefix and stream header are covered too. In practice every byte is authenticated, and the FINAL tag plus the "data after the end" check handle truncation and extension.
- The header shape and KDF limits are checked *before* the KDF runs, with only one KDF run per attempt.
- Verify-before-delete re-derives the key from the password and the header on disk, checks every chunk, and compares a hash. Temp file in the same folder, fsync, folder fsync, and cleanup on `BaseException`.
- One generic wrong-secret error, so the tool never reveals which secret or which part was wrong.
- Unlock is based on a hard link with no overwrite, the file name is cleaned, the internet mark is carried over, and risky extensions get a warning.
- Symlinks and hard links are refused; the overwrite is chunked so a large file never sits in memory.
- The menu uses HKCU only, `-P -E`, and an absolute package path; `menu_entries` is a pure function you can test.
- NFC normalisation of passwords, and tests around the chunk-size boundaries.
